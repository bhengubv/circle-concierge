# Concierge — implementation plan

**Purpose:** turn every requirement in [the product vision](CONCIERGE-PRODUCT-VISION.md) into sequenced, verifiable work. This plan is a queue, not a claim that its outcomes are implemented. A vision item is not complete until its acceptance evidence exists.

**Product:** Concierge owns the person's experience, durable work, workflows, continuity, and control. Circle AI supplies intelligence, capability discovery, and resource-aware model/device selection. Concierge shapes and builds the requested outcome, then dispatches eligible operational work to integrated Butler and monitors its progress, decisions, and results in the same Workspace or Project. Butler performs that dispatched work; Circle AI does not replace Butler's operational role. Butler's `IAIService` is the long-lived inference/tool service, `ICompanionSession` adds identity, context, active goals and proactive interaction, and ButlerAPI is a remote inference client. Concierge keeps ownership of durable work identity and person-facing controls; it discovers what the engine and environment can do, then presents those abilities in its own language without asking the person to make technical model/runtime choices. The initial authenticated Butler operation contract, Concierge account session, Project persistence, and monitoring surface now exist in source; live Butler execution and broader operation coverage remain unverified and open.

**Current architecture map:** [CONCIERGE-ARCHITECTURE-MAP.md](CONCIERGE-ARCHITECTURE-MAP.md). It records observed owners, persistence, boundaries, verified limits, and the specific runtime evidence still needed. Stage 0 remains open until that evidence is collected.

## Rules that apply to every stage

- Keep ordinary conversation lightweight. Do not force Chat into a project workflow.
- Use the same durable work identity as a person moves between Chat, Workspace, Project, and Start-Up.
- Give every submitted request one identity and one execution. Retries and connected clients must not duplicate work.
- For already-connected devices, preserve **route → execute → sync**: Circle AI routes using current capabilities and resources; the selected device executes once; then the result, progress, events, decisions, and artifacts sync to the other clients.
- Desktop is the first implementation target. Establish and demonstrate its product foundation before claiming Mobile or Wearable parity. Keep contracts portable so later heads do not need a different work model.
- Resource limits, offline operation, pending permissions, safety policy, and failed work are visible states with recovery paths, not silent failures.
- People can inspect, correct, pause, and review autonomous activity. External publishing, purchases, or other consequential actions obey the configured control level and explicit safety requirements.
- Preserve user changes and existing data. Prefer additive migrations and reversible changes.
- A design, API, mock, build, or passing unit test alone does not prove a user journey. Record what was exercised in a running app and on which head.

## Delivery queue

### 0. Baseline, ownership map, and verification harness

**Work**

- Map startup, Circle AI capability and model-selection paths, Chat, Workspace, Project/Workflow, tool execution, approvals, Creator, downloads, persistence, Away/LAN, Android, Windows, and Wearable.
- For each path, name the source of truth, owning service, persisted data, API/event boundary, UI entry point, and present test or manual evidence.
- Distinguish device capabilities (camera, microphone, sensors, network, available compute/storage) from Circle AI capabilities (planning, creation, coding, analysis, and other engine-supplied abilities).
- Record the real behavior on Desktop and Mobile separately. Do not infer Mobile behavior from shared Razor components or a successful build.
- Fix the known compile blocker and establish repeatable Desktop/Android builds and test commands. Add integration/manual scenarios for gaps that unit tests cannot cover.
- Preserve local data and user modifications; document migrations and backup/restore requirements before changing persistent stores.

**Exit criteria**

- An architecture map names owners and data flows for capability discovery, routing, execution, persistence, sync, approvals, downloads, artifacts, and recovery.
- Baseline builds and tests run; failures are either resolved or recorded with an owner and queue item.
- Every later acceptance criterion has a named verification method and target head/device.

### 1. Circle AI capability discovery and Concierge presentation

**Work**

- Define a versioned capability description supplied by Circle AI: stable id, person-facing name and description, availability/readiness, requirements, supported contexts, action/safety class, and changes/version.
- Discover capabilities and live device readiness/resources at runtime. Report only the information needed to choose and execute work; keep provider/runtime internals out of ordinary user flows.
- Let Circle AI choose the suitable model/runtime and execution device. Remove provider/runtime selection from Concierge's visible product UI; do not ask a person to diagnose resource fit.
- Make Concierge decide how available capabilities appear: contextual actions, composer affordances, Workspace/Project tools, or no visible control when irrelevant.
- Update the UI when capabilities appear, disappear, become busy, fail, or return, without requiring an app restart. Explain unavailable abilities in useful language and offer a next step.
- Keep engine abilities distinct from OS/device abilities and from external integrations requiring keys or permissions.

**Exit criteria**

- A changed capability response changes the appropriate Concierge surface without client hardcoding of model/provider choices.
- Unavailable or unconfigured features cannot be mistaken for ready actions; reappearing features become available without restarting.
- On Desktop, Circle AI automatically selects a resource-appropriate execution path, and the person is shown the useful outcome/status rather than technical model choice.
- Capability discovery, failure, and recovery are covered by automated contract tests and a running Desktop scenario.

### 2. Durable work identity, events, and recovery

**Work**

- Define a persistent work model shared by Chat, Workspace, Project, and Start-Up: work id, conversation/thread, request idempotency key, run lifecycle, events/cursor, plans, progress, decisions, approvals, agent activity, files/artifacts, and completion/review state.
- Define explicit states such as queued, preparing, running, waiting for a person, paused by a resource/network limit, failed with recovery, completed, and completed-needing-review.
- Persist before acknowledging. Support restart/resume from a durable event cursor; make retries idempotent and order concurrent submissions predictably.
- Preserve the original request, relevant history, context, and references when work is promoted from Chat to Workspace/Project or handed to another device.
- Define retention, deletion, export, migration, and local/offline semantics. Make the privacy boundary for device data, location, sensor data, and artifacts understandable.
- Keep one canonical record while allowing device-specific presentation and cached/offline views.

**Exit criteria**

- Restarting Desktop restores the current work, event position, pending approvals/decisions, and artifacts without replaying completed actions.
- Repeating a request with its original idempotency key produces one execution.
- Forced app shutdown, network loss, and host loss produce a truthful state and a tested resume/recovery path.
- A person can delete or export work according to the documented retention policy.

### 3. Chat, first-run experience, and action control (Desktop)

**Work**

- Keep Chat immediately usable without setup or project scaffolding. Support new threads, saved/recent conversations, history search/open/delete, and clear empty/error states.
- Let Concierge show assistant plans, progress, tool activity, results, and continuing runs. Switching threads must not orphan a run; returning should restore its state.
- Implement **Plan only**, **Ask first** (default), and **Act freely** as understandable action-control levels. Explain the practical effect, persist the choice, and enforce it consistently in all tool/agent execution paths.
- Make approval requests describe the action, target, scope, and consequence. Support review/allow/deny, waiting state, cancellation/expiry, and a truthful result. A person should never be trapped by an approval UI whose underlying run cannot stop or recover.
- Build first-run onboarding around a useful outcome, not a technical setup wizard. Explain Concierge and Circle AI in product language; let the person start a conversation or prepare a goal before model preparation finishes.
- Show download/preparation progress without blocking the workspace. Offer useful optional activity (describe a goal, prepare a first workspace, or explore a guided sample); retain it and let Circle AI continue when ready.
- Keep accepted preparation in an app-scoped background worker, not a screen event: navigation must not cancel a transfer. The explicit Stop action and app shutdown remain meaningful cancellation points.
- When Circle AI exposes multiple eligible model tiers, stage downloads from smallest to largest and make a usable smaller tier available while larger tiers continue in the background. Circle AI owns device-fit and tier choice; Concierge does not expose model selection.
- Offer a short, hands-on Concierge tutorial during preparation so first-run time teaches the product and is not just a progress screen. Keep it skippable, resumable, and available on Desktop and Mobile while the download continues.
- Honor accessibility, keyboard, screen-reader, scaling, reduced-motion, and responsive layout requirements on Desktop.

**Exit criteria**

- A new person can start a simple Chat, resume and find old conversations, follow a running task after switching threads, and delete history.
- A scripted tool action demonstrates all three control levels; Ask first is the initial state, and denied/stopped work does not later execute.
- A Desktop first-run journey remains useful through an interrupted/slow model download and resumes without losing the prepared goal.
- A multi-tier device trace shows one background transfer at a time in ascending size, useful readiness at the first compatible tier, continued preparation of eligible larger tiers, progress on every connected head, and no cancellation when the user navigates away.
- A new person can complete or skip the tutorial while preparation continues, then return to their saved goal without losing tutorial or work progress.
- Screenshot/manual evidence covers default, empty, active, approval-waiting, error, and completion states at supported Desktop sizes.

### 4. Workspace and Project modes

**Work**

- Workspace is a focused home for one or two related goals, with its own context, files, tools, outputs, run activity, and pending decisions.
- Project is a broader outcome containing multiple workflows and Workspaces. Support goal, scope, milestones, dependencies, decisions, assumptions, schedule/resource/budget estimates, deliverables, risks, and status.
- Replace fixed ordered `Workflow` as the only model with persistent, editable workflows that can branch, depend on other steps, pause, retry, recover, and be adapted by Circle AI to the stated goal.
- Show planned, active, blocked, awaiting-person, completed, and review-needed states. Keep artifacts and decisions attached to the work that produced them.
- Provide a small set of useful starting templates while letting Circle AI shape and revise steps. Do not force homework, creative work, or other goals into an app-development template.
- Promote Chat work into Workspace or Project without losing context/history; let scope grow from Workspace to Project when the person and Circle AI identify broader connected work.
- Keep Project/Workspace navigation understandable to nontechnical small-business and everyday users.
- Support the full build → execute → monitor loop in the owning Workspace or Project: Concierge keeps the person's goal, plan, durable work identity, permissions, and progress view; the integrated Butler execution capability performs the dispatched work; Concierge records and presents Butler's progress, outputs, and final status in that same context. Discover and document Butler's actual interface and ownership boundary before binding the two.
- Define a Concierge-owned Butler dispatch envelope containing the persistent Work/Project/Workspace IDs, run ID, idempotency key, action-control mode, approval references, cancellation signal, and event cursor. Butler tool calls must pass through Concierge's approval and audit boundary; Butler progress/results must return as attributable run events/artifacts. Duplicate dispatch, interrupted connection, cancellation, and app restart must not create duplicate execution or lose the work record.

**Exit criteria**

- A person can go from casual Chat to a focused Workspace and then to a multi-workflow Project without retyping context or creating duplicate executions.
- A sample project displays its workflows, dependencies, artifacts, key decisions, status, next step, and blocked reason after app restart.
- A workflow can be edited, resumed, retried, and recovered without silently losing completed work.
- The same project model supports at least one business workflow and one non-business/creative workflow without hardcoded app-development assumptions.
- A user can create or plan an outcome in Concierge, have eligible work dispatched once through the documented Butler integration, inspect live progress and approval/tool activity in the owning Workspace or Project, then navigate away or restart and recover the same run, results, and artifacts without replaying completed actions.

### 5. Visible agents, autonomy, and Start-Up Mode

**Work**

- Let Circle AI discover suitable agent capabilities and assign sub-agents within live environment limits. Resource limits—not a manually chosen swarm size—determine available concurrency.
- Show each agent's goal, owning Workspace/Project, state, output, resource constraint, and recent actions. Attribute changes and permissions to the responsible agent/run.
- Support pause, resume, correction, cancellation, review, and undo where possible. If undo is impossible, say so before the action and preserve an audit record.
- Ensure autonomy follows Plan only / Ask first / Act freely plus risk/safety policy. Keep external publishing, spending, irreversible changes, and account/security actions behind appropriate explicit approvals.
- Add **Start-Up Mode** above Project for business journeys spanning connected projects and workflows. Begin in plain language with **“New business or existing business?”** and let Circle AI shape a tailored path based on the person's actual goals and business.
- For an existing business, discover current context and avoid duplicating work; for a new business, guide the person from idea and validation through setup, launch, and operation. Neither journey should be a rigid one-industry checklist.
- Support autonomous company workflows only as observable, bounded work with permissions, budgets/limits, review points, interruption controls, and clear outcomes.

**Exit criteria**

- A multi-step Project can show concurrent agent work, capacity limits, outputs, and the next human decision; restart does not lose its audit trail.
- Pausing/cancelling stops eligible actions, reports any non-cancellable work, and preserves safe progress.
- A consequential action is correctly gated at every autonomy setting; approved actions remain attributable and reviewable.
- New-business and existing-business Start-Up journeys create meaningfully different, adaptable plans and connect their work to Projects/Workspaces.

### 6. Creative and general-purpose work surfaces

**Work**

- Surface Creator capabilities through the same engine capability discovery and Chat composer. Preserve the persistent canvas for Page, Slides, Video, Space, Sound, Phone, and Board; include visual history, undo/redo, save/restore, and work identity.
- Verify diagrams, configured Figma/Penpot imports, image generation, and available media tools as capabilities that appear only when ready/configured. Provide useful unavailable/permission/error states.
- Ensure generated/edited content, source references, versions, and exports become artifacts attached to the right Chat/Workspace/Project.
- Keep the system open to other task types (homework, music, video, research, and future capabilities) without assuming every new product needs a bespoke AI runtime selector.
- Preserve normal Chat for simple questions; offer creative/workflow surfaces when they help the goal, not as a mandatory flow.

**Exit criteria**

- Each of the seven Creator canvases survives navigation, app restart, history selection, and undo/redo without losing the latest saved state.
- At least one diagram, image, and media creation/import journey completes end to end when its provider/integration is configured; absent capabilities fail honestly and recover cleanly.
- Work produced in a creative surface is visible as an artifact in its owning durable work item and can be reopened/exported.

### 7. Route → execute → sync across Desktop, Mobile, and Wearable

**Work**

- Make Desktop the reliable execution host first: expose its current reachability and live capacity to Circle AI, accept routed work, persist one run, and publish its events/results.
- Connect Mobile as a full product head with device-appropriate UX. It should access Chat, Workspace, Project, capabilities, files, progress, approvals, and decisions; resource availability determines where execution occurs, not what the person can ask for.
- Prove both local paths: a request routed to a capable Mobile device and a heavier request routed to Desktop. Circle AI owns selection; the user does not pick a runtime.
- Make **Find Desktop work across networks**, including when Mobile is at a client site, shopping, or an event while Desktop remains elsewhere. Same-Wi-Fi discovery is only the first local check, not the remote-continuity solution. Prove remote reachability over the Internet using the agreed open proof setup, with network changes, duplicate delivery, disconnects, resume, and host hand-back covered. Keep that proof transport explicitly separate from production-secure pairing and do not imply that open Internet access is production-safe.
- After the selected device answers, synchronize durable events, run state, artifacts, and pending decisions to connected clients. Sync must not race the answer or start a second run.
- Preserve one work identity while keeping Desktop, Mobile, and Wearable interfaces suited to their screens; do not make them pixel mirrors.
- Add Wearable after Desktop/Mobile continuity: capture requests, monitor active work, receive important prompts, respond to decisions, and view concise change/recovery summaries. Never imply heavy work runs on the watch if it does not.
- Handle offline clients with ordered outboxes, cursor-based catch-up, stale resource reports, conflict rules, and safe retry semantics.
- Design pairing, identity, transport security, key lifecycle, and Internet relay/remote access as a separate hardening/release stage. No public production exposure without security review, authentication, and explicit deployment approval.

**Exit criteria**

- One real end-to-end trace proves: input submitted on one client → Circle AI selects the device from live capabilities/resources → one execution/answer on that device → events/results/artifacts sync afterward → another client continues that same work.
- Repeat/reconnect/offline scenarios do not duplicate execution or reorder requests; results converge after reconnection.
- Desktop-originated work can be monitored/responded to on Mobile; Mobile-originated light work can execute locally; heavy work can route to Desktop and return to Mobile.
- From a genuinely different network, Mobile can find and reconnect to the running Desktop, submit or continue the same durable work, and receive its result and progress without manual LAN discovery.
- Wearable can capture, monitor, and resolve an allowed prompt against that same durable work identity.
- Evidence records OS/device, build, network setup, steps, logs, and observed results. Do not claim the whole matrix from a build alone.

**Live evidence, 1 October 2026:** the connected Android app showed the Desktop's capability snapshot while the Desktop process exposed its LAN endpoint. This verifies discovery/capability visibility in the running Mobile UI, not a routed request, Circle AI's device choice, an answer, or synchronized run events. Keep those route → execute → sync criteria open.

### 8. Downloads, readiness, and productive waiting

**Work**

- Circle AI chooses the model/runtime appropriate to each device automatically. Keep that choice out of Concierge's ordinary UI.
- Where Circle AI exposes several tiers that fit, prepare them sequentially from smallest to largest; activate a usable tier as soon as it is ready, then continue larger-tier preparation without blocking Chat or other work.
- Run transfers in an app-scoped background service so navigating between Chat, tutorial, Workspace, or Project does not interrupt them. Keep per-device progress and readiness visible on every connected client; explicit stop and app shutdown still stop work cleanly.
- Show per-device preparation status and known progress, active/paused/ready/error state, and useful next steps on every connected client. Do not invent remaining time or imply readiness before it is true.
- Keep model readiness separate from work readiness. Let people learn the app, prepare a goal, and explore a sample during downloads; save their activity and continue it when Circle AI is ready.
- Preserve partial downloads across app restart, sleep, network change, and Desktop/Mobile connection. Avoid duplicate transfers or repeated restarts.
- Explain insufficient storage, unavailable network, host offline, unsupported device, cancellation, and recoverable download failures in plain language. Provide a useful retry/continue path.
- Add a Concierge .NET Host Manager for every .NET worker Concierge starts. It owns host identity/lifetime, live memory and CPU observations, per-device resource budgets, bounded concurrency, health/restart policy, idle shutdown, and clean pause/stop with durable work recovery. The person-facing Concierge process must stay responsive and bounded; an over-budget worker must be paused, stopped, or routed according to its work state rather than allowed to consume the device unchecked.

**Exit criteria**

- First-run users can prepare a useful goal while waiting, leave and return, and continue without losing input or restarting completed transfer work.

## Product-level acceptance journey

A person on any connected Concierge client can say: “Build an MVP for location-based product activation and BI.” Concierge understands the request, clarifies material assumptions, describes useful outcomes and known limits, and puts the work in the appropriate context. Circle AI uses live device resources and capabilities to select where one run executes. The person can follow the run, workflows, agents, permissions, decisions, and artifacts; answer important prompts; leave and return; and continue from another client without a duplicate run. If work is blocked, offline, or resource-limited, progress is preserved and the recovery choice is plain. The finish state says what is ready, what needs review, what did not complete, and what happens next. During model preparation, the person can prepare the goal or explore a guided sample. A simple question still feels like Chat, and a personal/creative request is not forced into a business-project template.

This journey is not accepted from a mock, design, build, or individual unit test. It requires recorded end-to-end runs on the named heads/devices and explicit evidence for every row in the vision coverage ledger.

### .NET Host Manager first Windows enforcement slice — 2 October 2026
