# Concierge architecture map

**Observed:** 1 October 2026. This records current code ownership and data flow to support Stage 0 of the implementation plan. It is a map of what exists, not a claim that the product vision is complete. Builds and unit tests do not establish the behavior of a running head.

## Main data flows

### Runtime and capabilities

- `CircleAiChatRuntime.LoadAsync` uses Circle AI's `DeviceProbe` and `DeviceAwareModelSelector` to choose a model from device resources. `IModelDownloadRequired` and `IChatRuntimeStatusEvents` expose pending selection, progress, readiness, and status to the isolated adapter and workspace.
- Desktop runtime evidence on 1 October 2026: the empty first-run screen appeared and the selected package began reporting progress (`config.json (1/10)`, 0 / 21,741.9 MB). Before any payload bytes were reported, the new Stop download control was clicked. The UI then displayed “Model download stopped. Circle AI can retry the download.” The process stayed open. This verifies Desktop first-run rendering, automatic selection/progress reporting, and the cancellation route; it does not verify a completed model download or Chat response.
- A first-run draft typed before a conversation exists is now stored in `SessionSnapshot.InitialDraftText`, restored only to the empty workspace, and promoted to that conversation's recoverable draft when sending begins. `SessionStateTests` and `WorkspaceComposerTests` verify persistence, restore, legacy session compatibility, and clearing after the user event is recorded. A clean Desktop process restart has verified recovery of a draft in an existing conversation; initial-draft-before-thread recovery across process restart remains unverified.
- The progress row is shared by Desktop and handheld Workspace. `IModelDownloadRequired.CancelCurrentDownloadAsync` now carries the stop action to both the in-process runtime and the isolated child host; the running Desktop trace exercised the isolated path. Mobile rendering and cancellation remain unverified on hardware.
- `IDeviceCapability` and `DeviceCapabilitySource` describe **device actions** such as device/network information, with live availability and risk. The current interface is not a versioned catalogue of Circle AI's product abilities (creation, analysis, coding, etc.).
- CircleAI 3.6.0 has a separate `CircleAI.Assistant` assembly with `Capabilities.All` (grouped conversation-start suggestions) and a `CapabilityRegistry`. The Desktop/handheld `WelcomePanel` reads the starter catalogue and places the selected opener into the editable composer draft. The registry's `ICapability` entries expose `ReadyAsync` plus `DoAsync` and are action handlers (for example, navigation, mode switching, translation, and media playback); they are not a general Circle AI engine-ability feed and should not be folded into the runtime capability catalogue as if they were. Separately, Circle AI's chat runtime now emits a versioned snapshot for conversation, tool use, image input, careful reasoning, and longer-context support. Optional abilities are checked against the Circle AI selector for the selected device; image input also requires accepted media types from the active generator. In-process heads refresh resources every 15 seconds; the isolated Desktop model host publishes the same periodic refresh across its process boundary. The welcome surface renders ready/preparing/setup-needed/unavailable states and the device resource summary with its measurement time. This snapshot does not describe the broader set of engine abilities or configured integrations. It is partial capability discovery, not closure of work item 2.
- Service-boundary check against the installed CircleAI 3.6.0 packages: `CircleAI.Hosting` supplies `IAIService`/`AIService`, which performs per-device model selection and can run a local Neuron specialist router; `CircleAI.Inference.Server` supplies a separate hosted HTTP inference server. Concierge references `CircleAI.Core` and `CircleAI.Inference`, not either service package. Its current `Concierge.Model.Host` is a child process controlled by Concierge over JSON-lines stdin/stdout, not an independently managed/discoverable service. A Circle AI service could benefit the multi-client vision, but a raw inference endpoint would not carry Concierge's durable work ID, action mode, approvals, events, or artifacts. Any service integration must preserve that Concierge-owned execution envelope and add live capability/resource reporting; this remains architecture work, not implemented behavior.
- `Concierge.Ai` still composes CircleAI.Core and Inference directly. `CircleAiLlmRuntimeService` probes a static list for its diagnostic room, while `CircleAiChatRuntime.LoadAsync` uses `DeviceAwareModelSelector` for actual chat model selection. A versioned Concierge snapshot carries measured memory/storage/CPU/connectivity and chat ability readiness across the isolated-host boundary, refreshed every 15 seconds while the runtime is alive. It does not yet join download state, connected-device availability, or a general capability registry into one feed.
- `WorkspaceBase.ChooseActiveRuntimeAsync` defaults to Circle AI when registered and otherwise chooses a ready runtime. The shared Web/handheld UI still has a different fallback behavior from Windows; do not infer one head's routing from another.

A ready local runtime stays local; Desktop is a fallback only when local Circle AI is not ready and Desktop can answer. This is client-side readiness fallback, not Circle AI selecting between two ready devices from live resources. ### Conversation, run, and event ownership

- `IConversationStore` is implemented by `ConversationStore` over `ConciergeChatDbContext` (SQLite). Conversations, message projections, and conversation events are stored separately. The database is per local data directory; it is not a shared cross-device database.
- `ConversationEvent` is the append-only conversation log. `(ConversationId, Seq)` is unique. Synchronization treats an already-known event ID as a duplicate and rejects conflicting sequence slots. Message rows can be rebuilt from the event log.
- `TurnRunner` is the shared turn loop called by Workspace and Away. It records conversation messages/events and owns model/tool iteration. `BackgroundRuns` tracks active cancellation sources in an in-memory concurrent dictionary; a process restart does not restore that register or its live `PlanProgress`.
- `TurnRunner` now writes a durable `TurnStart` event whose primary key is the request/run ID and whose payload fingerprints the submitted request, then a `TurnEnd` receipt with terminal status and answer metadata. Plans are written as run-linked `TodoWrite` snapshots when stated, revised, or advanced; a retry of a completed run restores the plan from its receipt, while an open run marker returns the latest persisted plan and an interrupted status. Retries with the same ID and payload replay a completed receipt; changed payload under the same ID is rejected; an interrupted run is not executed a second time. A duplicate insert collision is resolved from the stored marker/receipt. `ConversationRunGate` takes a stable OS file lock per conversation, so separate Concierge processes on one machine that share the lock directory serialize distinct turns; process acceptance verifies lock exclusion and release when a host is killed. Ordinary Workspace Chat persists a per-conversation retry key and canonical fingerprint in session state before execution, reuses it after reload only for the matching unclosed request, and clears it after a terminal receipt. Inline image generation also persists and reuses this identity. This is not a distributed lease and does not resume an interrupted run. Direct canvas actions remain outside the same submission identity path; the Away ledger remains separately persisted, and decisions, agents, approvals, and artifacts are not yet one run record.

### Tools, permissions, and approvals

- `AddConciergeTools` composes the registered tool sources into `IAgentToolRegistry`. `IToolCallScheduler` applies timeouts and hooks; `TurnRunner` invokes the scheduler and presents tool results as recorded events.
- `InteractiveToolApprovalService` owns the live pending queue observed by Workspace and Away. Approval decisions are connected to tool execution; the pending queue itself is not the durable Project/run state described by the vision.
- The composer defaults to Ask first and offers Plan only / Ask first / Act freely. The acceptance requirement remains to show that these modes are enforced across every execution route, including Away, agent, and external-action paths.

### Projects, workflows, and artifacts

- `Concierge.Shared.Delegation.Workflow` is a fixed, in-memory ordered list of delegates. It keeps completed step results for that invocation, but does not persist a user-editable workflow graph, dependencies, milestones, decisions, or recovery state.
- Separately, `IProjectStore` persists `ConciergeProject`, `ProjectWorkflow`, `ProjectWorkspace`, and `StartupJourney` documents in an additive SQLite store with optimistic revisions. `/projects` can create/edit business identity and context, connect Projects, and open a reviewable Start-Up planning draft in Chat. On first send, the conversation is durably linked to its Start-Up journey; `WorkspaceBase` restores that context from the linked conversation and `TurnRunner` carries the `StartupJourneyId` into tool scope. Start-Up turns expose `startup_read_context` and an approval-gated `startup_create_project`, which creates initial workflows/steps and atomically links the Project into the business journey. Project turns separately expose workflow create/update tools, including dependencies on visible steps across workflows. These are planning tools, not yet a live AI-generated/adapted plan; they do not project assistant activity into Project progress or synchronize these documents between devices. The in-memory `Concierge.Shared.Delegation.Workflow` and older file-backed routine stores remain separate execution paths.
- Web composition also registers routines and goals in file-backed stores. They are not yet unified with persistent Project/Workspace/Start-Up records.
- `IDesignStore` / `FileDesignStore` persists a versioned `DesignSessionSnapshot` in `design.json`: up to 30 moments, the current undo/redo position, and a still-valid selection. Older stores default to a one-moment session, and legacy single-document files remain readable. The document-only save path appends a history moment instead of dropping prior session history. Store and Creator-component tests verify reopening the visual strip at its saved selection; a real Desktop process-restart trace remains uncollected. Diagrams, image/media, and imports remain separate tool surfaces rather than one artifact ledger attached to durable work.

### Cross-device routing and sync

1. The handset/wearable creates or supplies a conversation ID and may send its local conversation-event snapshot with an Away request.
2. `AwayClient` posts the sentence and context to a discovered or configured host. The Desktop `AwayDesk` creates the matching conversation if needed, synchronizes incoming events, and calls the shared `TurnRunner`.
3. The host returns its answer and conversation events; the client can apply those events to its local store. Event IDs and sequence slots help make event import idempotent.

New Away submissions now persist their outbox request ID before delivery and send it as `requestId`. `AwayRequestLedger` stores a payload fingerprint and started/completed receipt under the host's local Concierge data folder. A completed retry returns its saved answer; a concurrent duplicate is serialized; a changed payload under a reused ID is rejected. If the host stops after recording `started` but before recording the answer, a retry is not executed again and tells the person to inspect the conversation first. This is at-most-once protection for Away delivery, **not** the vision's general durable run/event model or automatic interrupted-run recovery. Legacy callers without `requestId` remain on the old non-idempotent path. The receipt currently has no retention/deletion policy and its process-local lock does not coordinate multiple host processes.

This is a useful proof path, but it is not yet proof of the vision's end-to-end invariant. The new receipt protects Away retries only; it does not yet bind idempotency to a durable run/event/artifact record, resume an interrupted run, or cover Chat/agent submissions. No full offline/restart replay trace exists, and the Debug LAN bridge has no production security. The next cross-device gate must trace one phone request through route → exactly one Desktop execution → event/artifact sync, including a lost response, process restart, and offline recovery case.

### Durable Concierge → Butler dispatch recovery — 3 October 2026

The execute-and-monitor boundary is now explicit in the vision: Concierge owns the durable project and user controls, Circle AI supplies/selects intelligence and resources, and Butler executes dispatched operations and returns progress/results. The first implementation slice is still deliberately limited to Butler's read-only `find_jobs` capability.

To close the submit/acknowledgement crash window, Concierge now persists a `ProjectButlerRun` dispatch intent (including the stable idempotency key and exact request) before calling Butler. ButlerAPI exposes an owner-scoped lookup by idempotency key. On startup or a later monitor pass, Concierge reconciles that key first; if Butler already accepted it, Concierge attaches to the existing run. If no run exists and the person has not canceled, Concierge retries the same idempotent request. If the person canceled and Butler has no run, the intent remains visibly in its stopping state for a 30-second reconciliation window (to catch a submit still being committed) and then closes locally without dispatching; if Butler did accept it, the monitor requests cancellation and follows its terminal status.
