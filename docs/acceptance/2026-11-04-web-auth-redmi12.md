# Web protection and REDMI12 acceptance, 4 November 2026

The Web host previously allowed a Production process to start with no API key. It now refuses that configuration at startup. Development still permits an unset key. With a configured key, the existing `X-Concierge-Key` gate protects application routes; health and static assets remain reachable. Similar-looking paths such as `/healthz-private` are not exempt. The 16 focused authentication tests passed, and a Production launch without a key exited with the intended exception.

This is a containment step, **not phone-approved Web sign-in**. A browser does not send `X-Concierge-Key` by itself, and there is no owner-bound browser session yet. Do not publish the Web app as a usable personal Web client until the QR approval, owner binding, secure cookie, and data isolation have been implemented and tested. The existing `QrPairingChallenges` type is only a challenge store.

REDMI12 was identified over the existing ADB connection as a Redmi Note 12 Pro+ 5G (`22101316UG`). The first Android Debug build passed with 0 errors and 17 warnings. The device has Circle AI Service build 60. ADB's streamed installer returned `INSTALL_FAILED_USER_RESTRICTED` twice; copying the same signed APK to `/data/local/tmp` and calling Android's `pm install -r` returned `Success`. The phone's Circle AI approval required a biometric prompt, which the person completed.

Concierge then opened on REDMI12. With **Use Desktop** off, it sent `What is 2 plus 3?` and displayed `5`. The new-install SQLite `Messages` row records `ProducedBy = Circle AI Android service`, so this particular answer was local. This is a small service-path acceptance check, not proof of complex tasks, tool execution, image input, or Web sign-in.

The live settings screen showed “Connected to Circle AI service” beside a “Reconnect Circle AI” button. That was misleading; the button now reads “Manage Circle AI access” when connected and “Connect Circle AI” when approval is needed. The home screen also claimed the phone could not run a model before approval, despite missing authorization being the actual issue. It now directs the user to approve Circle AI on the phone. These UI corrections passed 42 focused component tests. The updated APK built with 0 errors and 17 warnings, installed in place with `pm install -r`, and the connected-state “Manage Circle AI access” label was visually confirmed on REDMI12.

The existing four-turn salon planning task in `2026-10-26-response-quality-tasks.md` was then run in a fresh REDMI12 conversation, with **Use Desktop** off. All four assistant rows in the device's SQLite store have `ProducedBy = Circle AI Android service`. This task **failed** its acceptance criteria. The first reply recommended Google Calendar and a contact form. The second diverted to SMS/WhatsApp and asserted an unverified free tier. The third proposed a name-and-email page whose data stays local to a customer's phone, which cannot by itself coordinate bookings. The final two-week plan omitted the five-hour weekly budget, provided no task estimates, and again assumed a WhatsApp Business API free tier. It did carry forward lunch and holiday blocking, and its Week 1/Week 2 headings rendered as rich text. No project or calendar action was claimed or performed.

On this 1080 × 2400 handset, typing a long prompt exposed a separate composer defect: the textarea shared a single row with file, camera, microphone, Desktop transfer, and Send controls, narrowing text to one or two words per line and obscuring earlier text. The handheld composer now places the full-width textarea above its controls. The rebuilt APK installed with `pm install -r`; a five-sentence correction was entered and remained legible at full width, with Send and the other controls on their own row. This is verified on REDMI12.

The correction explicitly required five hours per week, phone selection of open times, lunch and holiday blocks, and no assumed WhatsApp free tier. Circle AI answered locally, but still proposed browser-local storage for customer bookings and a static GitHub Pages deployment; that cannot coordinate availability or prevent double booking across customers. It gave no per-task hours, and the answer ended mid-phrase (`different br`). The complex planning task therefore remains failed even after correction. The UI fix does not establish answer quality or tool execution.
