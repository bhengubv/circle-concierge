# Windows Circle AI 3.9.2 handoff — 27 October 2026

## Verified live

- The tested release artifact is `CircleAIService-Windows-3.9.2-win-x64.exe`,
  SHA-256 `4438809D6054A7CB48B6FFC80FD767B17CAEAA778349D32C00992F50CB45AEC9`.
  A byte-identical copy is installed under
  `C:\ProgramData\Concierge\CircleAIService\bin\3.9.2`.
- Released binary inspection showed that the executable generates a fresh
  `X-Butler-Token` at startup and prints its loopback port and token to stdout.
  It does not read a configured port/token from the environment or register
  itself with Windows Service Control Manager. Concierge's host script captures
  those startup values without logging the token, authenticates `/v1/status`,
  checks `/v1/health` against the child PID, and atomically updates the
  protected `connection.json`.
- The protected connection retained explicit SYSTEM, Administrators, and user
  FullControl grants and the older service account Read grant after the handoff.
  Anonymous `/v1/health` returned HTTP 401. The authenticated endpoint returned
  HTTP 200.
- With the shared model store, 3.9.2 selected `Qwen3.5-4B-MNN` and reported
  `canAnswerSoon=true`, `canAnswerNow=false`: the installed model loads on a
  question. A direct authenticated `/butler/chat` question returned `4` in
  60.007 seconds. That time includes model loading and the HTTP request.
- The rebuilt Desktop app showed its conversation capability as Ready and
  completed one conversation with three turns: `3 + 2 → 5`, `5 - 1 → 4`,
  then, after moving the executable to ProgramData and restarting the host,
  `4 + 3 → 7`. The visible conversation and the SQLite message projection both
  contain those answers. Conversation ID:
  `E8CBE91E-42BB-4BCB-A76D-16B6ACBDA640`.
- SQLite message timestamp differences were 65.221, 85.716, and 174.797
  seconds from each user message to its assistant message. These are end-to-end
  message intervals, not pure inference times. The last turn includes a new
  service process and a longer conversation context.
- Twenty focused Windows service tests passed (0 failed, 0 skipped), including
  lazy-model first-turn acceptance, holding a connection handoff until an active
  answer ends, using a rotated connection on the next question without a
  manual refresh, and refusing to send to a stale endpoint when the handoff
  file disappears. The Windows Desktop build succeeded with 0 errors and 40
  warnings after those changes.
- The host script also launched and authenticated successfully under Windows'
  built-in PowerShell 5, independent of Codex's bundled PowerShell runtime.
- A per-user Windows logon task named `CircleAIService-3.9.2-User` was registered
  without elevation and started on demand. Its authenticated `/v1/health`
  reported PID 37276 at port 61611, matching the released 3.9.2 executable in
  ProgramData. Concierge Desktop then opened with Circle AI connected and got
  a fresh response through that task-managed host.
- The first crash test exposed a recovery defect: Task Scheduler left the
  manually started task stopped with result 1. The host script now restarts
  its one child with a bounded delay. In the repeated test, terminating PID
  44380 produced authenticated replacement PID 35116; terminating that host
  while Desktop was open produced authenticated replacement PID 41476. The
  task remained Running and the connection file rotated to each new port.
- Desktop briefly displayed the old refused port after the second rotation,
  then its existing ten-second readiness poll changed the conversation
  capability to Ready without manual input. The runtime also checks the
  protected connection before each question, so an idle handoff is not tied
  to a stale token.
- A new conversation sent after that recovery received `13` for `12 + 1`
  through the task-managed 3.9.2 host. Its saved user-to-assistant interval
  was 147.718 seconds, including cold model load. A later authenticated
  health read still matched the task's single live 3.9.2 PID, 41476.
- The task-managed host answered a request to quote previous assistant replies
  with `5, 4, 7, 8`. This demonstrates that the conversation's earlier answers
  reached the model across the host change. The earlier fourth answer of `8`
  to the apple-total question was incorrect; the correct total was `7`. The
  evidence points to answer quality, not missing conversation history. The
  incorrect answer took 97.132 seconds from saved user to assistant message;
  the exact-history request took 91.354 seconds. These include client and
  service time, not only inference.

## Still open

- A logon trigger is registered, and starting the task on demand is verified.
  A real sign-out/sign-in and full Windows reboot have not been performed.
- An administrator-level startup task was not installed: the prior UAC request
  was canceled. The per-user logon task gives this Windows user an independent
  host without that approval.
- The old 3.8.1 and 3.9.1 directories remain under `C:\Program Files\Concierge\CircleAIService`.
  Neither old executable is running. A direct, path-checked removal of 3.9.1
  was rejected by automatic approval review before execution. Removal remains
  required before claiming the old installation is gone.
- Two Desktop conversation journeys have been proved through this installed
  service. Watch, phone, and restart after a full Windows reboot remain separate
  acceptance work.
- Desktop Settings still reports that `Agentic work` cannot take effect with
  this loopback service contract. The released Windows 3.9.2 host inspected here
  wires embedded skills and its ask queue without a conversation store; this
  acceptance does not establish the larger SQLite skill library, long-term
  memory retrieval, or multi-step service work in Desktop chat.
