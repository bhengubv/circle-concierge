# Windows Circle AI 3.9.1 deployment diagnosis

## Result at 14:26 JST

The released 3.9.1 executable runs as a standalone process. It has **not**
successfully replaced the registered Windows service or answered through
Concierge. The existing SCM service was restored to 3.8.1 and responds on its
original authenticated endpoint. A separate lazy, report-only 3.9.1 diagnostic
process remains running; it is not Concierge's active backend.

## Evidence

- Released file SHA-256:
  `861B28130D59127CF2CDDFC2E6ECAB22F04F2B9FAE1D470F0EF350CEFFBB2491`.
  Product version `3.9.1+9884095b4cba5c68d3c48871627e98f90ca75fbe`.
- Replacing only the SCM executable path resulted in System events 7009 and
  7000: no SCM connection within 30,000 ms. The process then exited.
- Inspection of **released binary IL**, not a Circle AI source checkout, shows
  `CircleAI.Service.Host.Program.Main` ignores its command-line arguments,
  starts `HttpLoopbackEndpoint`, and waits for Ctrl-C. It contains no Windows
  service registration. It reads `CIRCLEAI_MODELS` and `CIRCLEAI_DATA` instead
  of the old host's command-line paths and production settings.
- Standalone deployment PID 30336: `/v1/health` and `/v1/status` returned HTTP
  200 on its announced loopback port. `/v1/diagnostics` returned HTTP 404.
  Authentication is the generated `X-Butler-Token`, not the old host's
  `X-CircleAI-Api-Key`. No token is included in this record.
- The service selected **Qwen3.5-4B-MNN**. Its own setup report measured
  **2,629,387,626 / 2,845,944,094 bytes**, displayed as 92%.
  `/v1/status` returned brain phase `NoModel`, `canAnswerNow=false`, and
  `canAnswerSoon=false`. The model directory existing does not mean it is ready.
- Diagnostic environment: existing shared model root, separate owned
  `service-3.9.1` state directory, `CIRCLEAI_LAZY=1`, `CIRCLEAI_UPKEEP=report`.
  Downloads and reclamation are deliberately disabled for this diagnosis.
  This is not a production setup or an automatic-download acceptance test.
- Model inventory remained 33 files / 35,410,223,670 bytes before and after.
  This compares names/count/size only; it is not a byte-by-byte preservation test.

The initial capture process (9072) was stopped after confirming it listened,
solely to replace buffered capture with live log files. PID 30336 is that
replacement, not evidence of crash recovery. The initial upgrader draft was
removed from `scripts/` into local `work/` because it assumes the old SCM/API
contract and is unsuitable for this released host.

Local evidence: `work/2026-10-23-windows-service-upgrade.log`, System events,
`work/released-3.9.1-host.cs`, `work/released-3.9.1-loopback.cs`,
`work/windows-3.9.1-startup-stack.txt`, and protected diagnostic stdout/stderr.
The stdout contains a generated credential and must not be committed or shared.

## Required next work

Choose an appropriate persistent process host for this executable, discover its
announced endpoint/token securely, and consume its actual readiness and queued
request API in Concierge. Complete/resume the service-selected model through the
service's setup path, then prove Desktop and watch answers. Do not treat a longer
SCM timeout, HTTP 200, or a package version as completion of that journey.
